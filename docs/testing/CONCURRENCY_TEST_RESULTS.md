# 第一轮并发处理验证（2026-10-08）

## 发现与修复

改动前：同时提交只读任务会并行访问设备；初始登录已能合并，但 6 次并发 renew 导致 6 次重新登录。在模拟“最新登录使旧会话失效”的设备上，过期会话并发恢复出现 HTTP_403。这是模拟复现，不代表已确认真实 T830 的会话失效策略。

改动后：一个 T830 实例的 run/query/write/rpc 通过 FIFO 队列执行完整工具任务。登录、辅助诊断及重试包含在任务内，不被下一工具任务插入。操作失败时队列仍继续。renewPromise 合并同时到达的会话更新；login 会等待正在进行的更新。

queue 诊断记录包含 operationId（实例内唯一任务编号）、waitMs（排队时间，毫秒）和 policy=fifo_per_device_instance。排队时间与设备响应时间是不同概念。

## 模拟自动验证

node --test：17 项全部通过，其中新增 6 项并发测试：

1. 六个并发任务只初始登录一次，按进入顺序处理，模拟设备同时处理的 HTTP 请求最大值为 1。
2. 六次并发 renew 共用一次重新登录。
3. 四个并发查询遇到过期会话，只更新一次，后续任务使用新会话。
4. 权限错误和网络超时后，后续任务仍完成；只读超时重试仍有上限。
5. 五个并发 MCP 调用经真实 SDK Client/stdio 完成，任务编号不重复，设备端串行。
6. 登录缺少凭据时，所有排队调用均明确失败，不挂起。

## 真实设备验证

node scripts/concurrency-smoke.mjs 同时提交两批现有只读工具调用，关闭写工具：

- 第一批：wifi、version、mesh_status、dhcp、workmode、country，共 6 个正常返回。
- 第二批：mesh_status 正常、share 返回已知 Object not found、version 正常。share 失败未阻断后续任务。
- 合计 9 次调用，8 正常、1 已知错误；每条都有队列记录及唯一任务编号。

完整结果：reports/live/concurrency-smoke-results.json。原 48 项 smoke 报告未覆盖。这不是设备吞吐量测试，也没有主动使实机会话失效；会话冲突与更新合并主要由模拟场景验证。

## 执行边界

队列只协调同一 Server 中共享 T830 实例的工具入口。其他进程、设备网页、其他客户端实例及直接调用底层 request/rawRpc 不受此队列协调。外部客户端仍可能改变设备状态或会话。

每次一个完整工具任务，不等于多个工具组成的业务任务具有事务性；未来写配置与回读如果分成两个工具调用，仍需另行设计执行边界。

请求超时限制不包含排队等待。MCP 客户端超时也尚未实现排队取消。因此本轮仅验证小批量任务，不承诺无限队列、高负载、取消或关闭 Server 时的任务处理。下一轮可按实际业务需要补充队列长度、等待上限及取消处理。

没有引入优先级，没有新增设备 API，没有执行真实配置写入。
